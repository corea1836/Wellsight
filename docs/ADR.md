# Architecture Decision Records

## 철학
- MVP는 단순하게 만든다. 서비스 동작과 본인 테스트에 필요한 것만 만들고, 공개 출시에 필요한 것은 P4로 미룬다
- 웰니스 경계 안에 머문다. 진단·치료처럼 보이는 표현은 쓰지 않는다
- 판정은 규칙이 하고 설명은 AI가 한다. AI는 판정을 바꾸지 않는다
- 근거 있는 출처를 쓴다. 판정 기준, 습관, 위급 수치에는 출처를 붙이고 본인이 검수한다

---

### ADR-001: Next.js + FastAPI + Supabase, 모두 서울 리전
**결정**: 웹은 Next.js(Vercel), API는 FastAPI(Cloud Run), DB·인증은 Supabase(Postgres·Auth, Google 로그인)를 쓴다. Supabase Storage는 쓰지 않는다. 구독 결제는 Polar로 P4에서 연동한다.
**이유**: P4에서 결과지 추출을 서버 내장 모델로 바꾸려면 Python 서버가 필요하다. 건강 데이터는 서울 리전에 둔다.
**트레이드오프**: MVP만 보면 FastAPI 없이도 만들 수 있다. 언어와 배포 대상이 두 개라서 관리 비용이 늘어난다.

### ADR-002: 브라우저가 FastAPI를 직접 호출
**결정**: 브라우저는 Supabase access token을 Bearer로 붙여 FastAPI를 직접 호출한다. 업로드도 브라우저에서 FastAPI로 바로 보낸다.
**이유**: Vercel 함수의 요청 본문 4.5MB 제한을 피한다. Cloud Run의 32MB 제한에 맞추기 위해 사진은 브라우저에서 축소한다.
**트레이드오프**: CORS 허용 목록을 직접 관리해야 한다.

### ADR-003: 판정은 규칙 데이터로만
**결정**: 결과지의 기관 판정·참고치를 그대로 쓰고, 없으면 「건강검진 실시기준」 별표4를 따른다. 추가 검사는 결과지 참고치로 판정한다. 판정·위급 여부는 순수 함수가 계산하고, AI는 설명만 한다.
**이유**: 판정의 정확성과 재현성을 확보하고, 웰니스 경계를 지킨다.
**트레이드오프**: 혈액검사 기준은 기관마다 달라서 규칙 데이터를 관리해야 한다. 근거가 없는 항목은 '판정 없음'으로 둔다.

### ADR-004: 웰니스 가드레일은 프롬프트 지시만
**결정**: 금지 표현(질환명 단정, 질환 가능성, 발병위험도, 신체나이, 약물·치료 조언)을 프롬프트에 넣고 면책 고지를 표시한다. 출력 후처리 필터는 두지 않는다. 유권해석은 문제가 생길 때만 받는다.
**이유**: MVP를 단순하게 유지한다. 식약처 웰니스 기준(2026.2 개정)은 만성질환자에게 생활습관을 추천하는 것을 웰니스로 본다.
**트레이드오프**: 모델이 지시를 어기면 금지 표현이 그대로 노출될 수 있다.

### ADR-005: MVP 추출은 Claude, 원본은 보관하지 않음
**결정**: MVP에서는 결과지 원본(이름·주민번호가 포함될 수 있음)과 식단 사진을 Claude로 보내 추출한다. 마스킹은 하지 않는다. 원본은 요청 안에서만 쓰고 저장하지 않으며, 사용자가 확인한 구조화 값만 저장한다.
**이유**: 서버 내장 모델 없이 빠르게 만들 수 있다. 원본을 저장하지 않으면 유출 위험이 줄어든다.
**트레이드오프**: 원본이 국외(Anthropic)로 전송된다. 그래서 국외이전 동의 문구에 이 사실을 명시하고, 서버 내장 모델로 바꾸는 것을 공개 출시 조건으로 둔다. 확인 전에 나가면 다시 올려야 한다.

### ADR-006: 용도별 모델 — 분석은 Opus, 식단 사진은 Sonnet
**결정**: 결과지 추출·검진 해석·습관 추천·주간 리뷰·월간 회고는 Opus 5.5(`claude-opus-5-5`)를 쓰고, 식단 사진 분석은 Sonnet 5.5(`claude-sonnet-5-5`)를 쓴다. 모델 ID는 `llm` 래퍼 설정 한 곳에서 관리한다.
**이유**: 추출값이 틀리면 판정도 틀리므로 정확도를 우선한다. 사용자가 적어서 비용 차이는 작다. 식단 사진은 단순 인식이다.
**트레이드오프**: Opus는 Sonnet보다 비싸다(1M 토큰당 입력 $4·출력 $20, Sonnet은 $2·$10). 대신 일일 비용 한도로 상한을 둔다(ADR-009).

### ADR-007: AI 생성 시점과 결과 재사용
**결정**: 검진 해석은 확인된 값을 저장하면 자동으로 1회 생성한다. 주간 리뷰는 마지막 주간 리뷰로부터 7일, 월간 회고는 마지막 월간 회고로부터 30일이 지나면 생성 버튼만 활성화한다. 생성한 결과는 저장해서 다시 쓰고, GET 요청은 AI를 호출하지 않는다.
**이유**: AI 호출 횟수와 비용을 예측할 수 있다. 리뷰는 사용자가 원할 때 만든다.
**트레이드오프**: 사용자가 원해도 재생성할 수 없다. 생성 이후의 기록은 다음 리뷰에서만 반영된다.

### ADR-008: AI 리뷰는 생성 당시 기록 기준, 무료 달성률은 최신 기록 기준
**결정**: AI 리뷰는 분석 범위, 생성 당시 입력 요약, 생성 시각을 저장하고, 소급 입력이나 새 검진이 생겨도 바꾸지 않는다. 무료 주간 달성률(달력 주)은 최신 기록으로 계속 계산한다.
**이유**: 재생성 없이 리뷰를 일관되게 유지한다.
**트레이드오프**: 화면마다 달성률 숫자가 다를 수 있다. 그래서 AI 리뷰에는 '○월 ○일 기록 기준'을 표시한다.

### ADR-009: 비용 차단은 일일 비용 한도 하나
**결정**: 결과지 추출과 식단 사진 분석에는 상품 사용량 쿼터를 두지 않는다. `llm` 래퍼가 호출 전에 `ai_usage`의 오늘(KST) 비용 합계를 확인해서, `AI_DAILY_BUDGET_USD`(기본 5) 이상이면 AI 기능만 `ai_paused`로 막는다. 막힌 기능은 다음 날 KST 0시에 풀린다. Anthropic Console 월 한도($30)도 건다. 분당 요청 제한은 두지 않는다.
**이유**: P4 전에는 가입이 제한되어 있어 사용자가 본인뿐이다. 그래서 차단기는 가장 단순한 형태로 충분하다.
**트레이드오프**: 한 사용자가 한도를 다 쓰면 전체 AI 기능이 멈춘다. 공개할 때는 다시 검토해야 한다.

### ADR-010: P4 전 가입 제한과 수동 Pro 부여
**결정**: P4 전까지 허용 이메일 목록(`ALLOWED_EMAILS`)에 있는 사용자만 쓸 수 있다. Pro 권한은 `subscriptions` 행을 SQL로 직접 넣어 부여한다(출처 manual).
**이유**: 법적 체크리스트를 갖추기 전에 다른 사람의 건강 데이터를 처리하지 않는다. 결제를 연동하기 전에도 Pro 기능을 테스트할 수 있고, 권한 확인 로직은 P4 이후와 똑같이 쓴다.
**트레이드오프**: 공개하려면 제한을 해제하고 Polar를 연동하는 작업이 필요하다.

### ADR-011: 알림·PWA 제외, 반응형 웹만
**결정**: 알림 없이 사용자가 직접 방문한다. 알림과 PWA는 나중에 함께 추가한다.
**이유**: MVP를 단순하게 유지하고, 알림 없이도 습관이 만들어지는지(H3) 검증한다.
**트레이드오프**: 재방문율이 낮아질 수 있다.

### ADR-012: 날씨 맞춤은 규칙만
**결정**: 라이브러리 습관에 붙은 날씨 태그와 미리 작성한 대체 습관·문구로 그날의 습관을 바꾼다. AI는 호출하지 않는다. 질병관리청 건강수칙 출처를 표기한다.
**이유**: 매일 AI를 호출하는 비용을 없애고, GET 요청에서 AI를 부르지 않는다는 원칙을 지킨다.
**트레이드오프**: 문구가 다양하지 않다. 대체 문구도 라이브러리 검수 대상이 된다.

### ADR-013: 검수된 습관 라이브러리
**결정**: 개발 단계에서 AI가 항목군별 습관 초안을 만든다. 근거는 공공기관·학회 가이드라인을 우선하고, 그다음 학술지를 쓴다. 본인이 검수하고(인용 문헌이 실제로 있는지와 내용이 맞는지는 필수 확인) 출처와 함께 저장소 JSON으로 둔다. 런타임 AI는 목표 설정 때만 선택·개인화한다.
**이유**: 근거 없는 건강 조언을 막는다.
**트레이드오프**: 라이브러리에 없는 항목군은 설명만 하고 습관을 추천하지 않는다.

### ADR-014: 데이터는 FastAPI만 다룬다
**결정**: 앱 테이블은 `app` 스키마에 두고 Supabase Data API에 노출하지 않으며 RLS를 건다. 프론트는 데이터를 직접 읽지 않고, FastAPI 응답을 단일 출처로 쓴다.
**이유**: anon 키로 건강 데이터를 조회하는 경로를 없앤다.
**트레이드오프**: 모든 데이터 API를 FastAPI에 직접 만들어야 한다.

### ADR-015: 시드는 저장소 JSON
**결정**: 표준 항목, 판정 기준, 위급 수치, 습관 라이브러리, 시도 좌표는 저장소 JSON으로 관리하고 관리자 화면은 두지 않는다. DB에는 식약처 음식 데이터(검색용)만 적재한다.
**이유**: 검수 이력을 git으로 남기고 MVP를 단순하게 유지한다.
**트레이드오프**: 시드를 바꾸려면 배포해야 한다.

### ADR-016: 본인 테스트 기간은 무료 인프라
**결정**: 본인 테스트 기간에는 Vercel Hobby, Supabase Free(dev/prod 2개), Cloud Run 무료 범위로 운영한다. P4 공개 전에 Vercel Pro와 Supabase Pro로 전환한다(약 $45/월).
**이유**: 검증 전에는 비용을 쓰지 않는다. Vercel Hobby는 비상업 용도만 허용한다.
**트레이드오프**: 백업이 없어서 데이터 유실 위험을 감수한다. Supabase Free는 1주일 동안 활동이 없으면 일시정지된다.

### ADR-017: 동의는 최소한만, 법령 검토는 P4
**결정**: MVP는 민감정보·국외이전 체크 2개와 동의 시각·문구 버전만 저장하고, 철회는 탈퇴로 처리한다. 개인정보·법령 관련 추가 검토와 세부 설계는 P4 준비 단계에서 진행한다.
**이유**: 현재 MVP는 서비스 동작과 본인 테스트에 집중한다. 민감정보는 별도 동의(개인정보 보호법 제23조), 국외이전도 별도 동의(제28조의8)가 필요하다.
**트레이드오프**: 공개 전에 동의 관리 흐름과 법적 체크리스트를 따로 만들어야 한다.
